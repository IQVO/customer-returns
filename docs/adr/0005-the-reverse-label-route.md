# 5. The reverse-label route: the one in-org call

## Status

Accepted (2026-11-14).

## Context

A physical return needs a label the shopper can hand to a carrier. The ship-to — the one piece of PII a label needs — lives in the shipping context, and the network's PII rule (wave-4 design, F25) says this context never reads it. The shipping context therefore owns reverse labels the way it owns outbound labels, and this context calls it over the one in-org route the network allows (the pattern vendor-connectivity already uses for `POST /labels`).

## Decision

- **The call.** `POST /return-labels` on the shipping context (its ADR 0015, migration 0005): body `{returnAuthorizationId, orderId, packageNo, destinationPostalPrefix}`; answer `{trackingNumber, carrier}`. The client is `internal/adapters/outbound/labels` — the ONLY outbound HTTP client of this context — and implements `ports.LabelIssuer`.
- **Config-gated, tolerant.** `SHIPPING_LABELS_URL` (default empty) enables the route; with it unset — or on any transport failure, non-200 answer, or a body without a tracking number — the client answers `ports.ErrLabelUnavailable`, the label use case answers `422 label-unavailable`, and NOTHING else happens: no 500, no retry storm, no outbox row. The authorize-and-link flow stays available and honest until the route and its config ship.
- **Idempotent by construction.** The client sends `Idempotency-Key: <returnAuthorizationId>:<packageNo>`, restating the pair the shipping context dedupes RETURN labels on; a retry is a replay.
- **Outside the unit of work.** The HTTP call runs BEFORE the transaction: the use case asks for the label, then ONE transaction re-reads the aggregate, links the tracking number (`LinkLabel`, ≤ 5) and appends `ReturnLabelIssued`. A failure between the call and the commit is healed by the shipping context's dedupe on the retry.
- **What this context keeps.** The tracking number and the destination node id — never the address, never the label PDF. The shopper-facing tracking view is THIS context's authorization (stated in the shipping context's ADR); the reverse label does not start a package journey and scans of reverse packages are counted-and-acknowledged unknowns there.
- **The pickup stop groups by construction (F3).** The shipping context computes the reverse label's stop key with the same secret over the same ship-to, so a later PICKUP groups with the original delivery stop; this context knows nothing of that mechanism.

## Consequences

- This context has exactly one synchronous seam, config-gated and tolerant; everything else is events.
- When the route answers anything but 200, the shopper sees `422 label-unavailable` and may retry later with the same `Idempotency-Key`; the authorization itself is unaffected.
- The e2e integration test drives a stub of the route (issuing `RN-RET-*` tracking numbers, answering 503 for one package) to pin both sides of the contract.

## Addendum 2026-11-16: the route answers 201

The Decision and the Consequences above name 200 as the answer that carries a label. The route as the shipping context shipped it (its ADR 0017 and migration 0007, the numbers that replaced the 0015 and 0005 named above) answers `201 Created` with a `ReturnLabel` body, and a replay of the same `Idempotency-Key` answers that first response again: `201` plus `Idempotency-Replayed: true`, never `200`. Read "non-200" and "anything but 200" above as "anything but 201": `201` is the one success the client accepts, and every other answer, `200` included, stays `ports.ErrLabelUnavailable`. Nothing else of the Decision changes: the client still reads only `trackingNumber` and `carrier`, both required properties of `ReturnLabel`, and every error the route documents (`409`, `422`, `503`) still maps to `422 label-unavailable`.

## Addendum 2026-11-17: the destination prefix is the return destination node's

The Decision above names `destinationPostalPrefix` in the body of the call and does not say where it comes from. The first cut sent the order group's prefix (`OrderGroup.DestinationPostalPrefix`, fed by customer-ordering's `CustomerOrderPlaced`), which is the OUTBOUND destination: where the shopper lives. The provider's contract asks for the opposite end (shipping-and-tracking `docs/adr/0017-reverse-return-labels.md` and `apis/openapi.yaml`, path `/return-labels`): `orderId` names the outbound order whose ship-to is the return's PICKUP address, and `destinationPostalPrefix` is the RETURN DESTINATION's prefix, which only the caller knows and which the provider prints on the label as it receives it. A label issued with the first cut would have been addressed to the shopper's own prefix, and the provider could not detect it. The client is off in every deployment (`SHIPPING_LABELS_URL` unset), so no such label was issued. Nothing of the Decision is withdrawn; this addendum records what the call sends.

- **What is sent.** The label prefix of the authorization's destination node (`ReturnAuthorization.DestinationNodeID()`: the region's returns centre for NEAREST_RETURNS_CENTER, the fulfilling node for ORIGIN_NODE; KEEP has no destination and links no label). `usecases.labelDestinationPrefix` reads it from the node half of the ReturnsNetworkView (`network.Node.LabelPostalPrefix`, column `returns_network_nodes.label_postal_prefix`, migration `0005`), which keeps it from the postal code node-topology publishes on `NodeRegistered` (ADR 0003, addendum of the same date). No sibling is called to look it up.
- **The rule is the provider's.** `network.LabelPostalPrefix`: the first 5 characters of the node's postal code after keeping only ASCII letters and digits, upper-cased; the whole remainder when it is shorter. The field belongs to the provider's contract, so this context conforms to the provider's own rule for a label prefix: shipping-and-tracking ADR 0002, A10 ("the first 5 letters or digits of the normalized postal code, the whole code when shorter") and `internal/application/shipto/shipto.go` (`PrefixLen = 5`, `Alnum`, `PostalPrefix`). The provider's `Alnum` keeps Unicode letters and digits; this context keeps ASCII only, so the value always matches the route's `^[A-Z0-9]+$`. For a postal code made of ASCII letters, digits and separators the two give the same prefix: `07750-000` is `07750`.
- **It is not customer-ordering's prefix.** `destinationPostalPrefix` on `CustomerOrderPlaced` is the first 3 characters of the shopper's postal code (customer-ordering ADR 0002 A10, `internal/domain/shipto/shipto.go`, `PrefixLength = 3`). It is a different field with a different purpose: here it resolves the region of the order group (`authorize.go`, the lookup in `service_area_prefixes`), and it keeps that use unchanged. It is never sent on the label call.
- **Finding for the provider, not changed here.** The provider's OpenAPI constrains `destinationPostalPrefix` to 1..16 characters of `^[A-Z0-9]+$` and does not state the length its own rule cuts a label prefix at. A caller reading only the OpenAPI cannot know that 5 is expected. That is a gap in shipping-and-tracking's contract to raise there.
- **Tolerant when the prefix is not known.** When the destination node is not in the node read model, or is there without a label prefix (a node registered before migration `0005`, or a postal code that holds no letter or digit), the use case answers `ports.ErrLabelUnavailable`, i.e. `422 label-unavailable`: the route is NOT called, nothing is linked, no event is appended. This is the tolerant failure of the Decision, extended from "the route is off" to "the destination is not known here yet"; it is never a 500. Rows written before migration `0005` get their prefix from the rebuild in the runbook (Rebuilding a read model from its topic), which is a precondition of ever setting `SHIPPING_LABELS_URL`.
- **What this context keeps.** Still the tracking number and the destination node id. Of a node's postal code only the label prefix is kept, never the code. A node is a building of the network, so neither is personal data; the shopper's ship-to still never enters this context.
